# 광고 제작 입력·출력 설계

작성일: 2026-09-16 · 갱신일: 2026-09-30 · 단계: 웹 화면·API 경로·편집 및 저장 구현 완료, 로컬 실제 API 평가와 프롬프트 개정 후 재평가 완료, 배포 환경 비밀값 연결 전

## 1. 첫 화면에서 할 일

판매자는 한 번에 대표 상품 하나를 홍보한다. 기존 3D 옷장의 여러 옷 조합은 코디 참고 이미지로 활용한다. 대표 상품 이외의 코디 아이템이 판매 상품에 포함된다고 오해할 문구는 만들지 않는다.

화면은 다음 세 영역으로 구성한다.

1. 상품과 코디: 기존 3D 옷장 또는 판매자가 고른 상품 사진.
2. 광고 요청: 상품 사실 정보와 광고 조건.
3. 결과 편집: 초안 3개 중 하나를 선택하고 직접 고쳐서 저장.

## 2. 입력 항목

### 필수 상품 정보

| 표시 이름 | 입력 방식 | 예시 | 제한 |
| --- | --- | --- | --- |
| 매장명 | 텍스트 | 오후옷장 | 1–40자 |
| 상품명 | 텍스트 | 스트라이프 반팔 티셔츠 | 1–80자 |
| 상품 종류 | 선택 | 상의 | 상의·하의·모자 |
| 색상 | 텍스트 | 화이트·네이비 | 1–40자 |
| 상품 특징 | 짧은 항목 추가 | 가로 스트라이프 / 라운드넥 / 반팔 | 1–5개, 항목당 1–100자 |

### 선택 상품 정보

| 표시 이름 | 입력 방식 | 처리 |
| --- | --- | --- |
| 소재 | 텍스트, 최대 100자 | 없으면 추측하지 않는다. |
| 판매가 | 원 단위 정수, 0–100,000,000원 | 실제 결제할 판매가로 입력한다. 할인율을 다시 곱하지 않는다. 미입력과 0원은 다르다. |
| 할인율 | 1–99% 정수 | 판매자가 확인한 할인율만 입력한다. 할인 홍보를 고르면 필수다. |
| 상품 사진 | 기기에서 선택 | 광고 카드 이미지에 사용한다. 첫 버전의 텍스트 생성 요청에는 보내지 않는다. |

문자 수는 앞뒤 공백 제거 후 유니코드 코드 포인트 수로 센다. 빈 선택 항목은 서버 요청에서 `null`로 전달하며 숫자 0이나 빈 문자열로 대신하지 않는다. 서버는 모델을 호출할 때 `null` 항목을 뺀다. 그대로 보내면 모델이 "소재 정보는 제공되지 않았습니다"처럼 없다는 사실을 문구에 쓰기 때문이다(2026-09-30).

### 광고 조건

| 표시 이름 | 선택지·기본값 |
| --- | --- |
| 사용처 | 첫 버전은 인스타그램 게시물 |
| 고객층 | 기본 ‘일상 캐주얼 코디를 찾는 고객’; 최대 80자로 수정 가능 |
| 말투 | 친근하게 / 담백하게 / 활기차게, 기본 ‘친근하게’ |
| 홍보 목적 | 상품 소개 / 신상품 소개 / 할인 홍보, 기본 ‘상품 소개’ |
| 마지막 안내 | 상품 보기 / 매장 방문 / 문의하기, 기본 ‘상품 보기’ |
| 추가 요청 | 선택, 최대 300자 |

추가 요청은 표현 방식에 대한 요청이다. 새로운 소재·가격·할인·재고 등의 사실을 추가 요청에 적어 상품 정보와 충돌시키면 생성 전에 상품 정보부터 정리하도록 안내한다. 의미 충돌 감지는 형식 검사만으로 보장할 수 없으므로 별도 평가가 필요하다.

## 3. AI가 돌려주는 결과

한 요청에 서로 다른 관점의 초안 3개를 제안한다.

| 초안 | 관점 |
| --- | --- |
| 1 | 입력한 상품 특징을 중심으로 소개 |
| 2 | 다른 옷과 함께 입는 코디 아이디어 제안 |
| 3 | 주말 외출 등 일상 장면에서의 스타일 제안 |

각 초안은 제목 40자 이내, 본문 220자 이내, 마지막 안내 40자 이내, 해시태그 3–6개로 구성한다. 해시태그 하나는 20자 이내이며 데이터에는 `#` 없이 저장하고 화면·텍스트 저장 시 붙인다.

‘코디 제안’과 ‘일상 장면’은 활용 아이디어로 표현한다. 방수·보온·신축성·다리 보정 효과 등 입력하지 않은 성능이나 착용 효과를 만들어내지 않는다. 판매가는 이미 할인이 반영된 금액이므로 정가나 할인 전 가격을 만들지 않는다.

문체는 프롬프트로 다음을 피하게 한다: '단순한 ~가 아니라 ~' 같은 대조 구조, 구호와 격언, '세련된'·'깔끔한' 같은 입력에 없는 평가어, 억지 삼단 구성, 같은 말로 시작하는 문장, '궁금하시면 문의해 주세요' 같은 군말. 이 규칙은 blader/humanizer(MIT)의 패턴을 한국어 광고 문구에 맞게 옮긴 것이다. 자동 검사가 위반 후보를 찾지만 최종 판단은 사람이 한다.

결과 형식이 올바른 것과 광고 내용이 사실에 맞는 것은 별개다. 구조 검사를 통과했다고 ‘사실 검증 완료’ 또는 ‘그대로 게시해도 안전함’으로 표시하지 않는다.

## 4. 사용자가 볼 예시

아래는 설명을 위해 직접 작성한 가상 예시이며 API 생성 결과가 아니다.

입력

- 매장: 오후옷장
- 상품: 화이트·네이비 스트라이프 반팔 티셔츠
- 특징: 가로 스트라이프, 라운드넥, 반팔
- 판매가: 29,000원
- 말투: 친근하게

예상 결과 형식

> 오늘의 스트라이프 한 벌
>
> 화이트·네이비 가로 스트라이프에 라운드넥을 더한 반팔 티셔츠예요. 오후옷장에서 29,000원에 만나보세요.
>
> 상품 정보를 확인해 보세요.
>
> #오후옷장 #스트라이프티셔츠 #반팔티

전체 초안 3개와 요청 데이터는 [example.json](ads/example.json)에 있다.

## 5. 결과 편집과 상태 처리

| 상태 | 화면 동작 |
| --- | --- |
| 입력 전 | 실제 생성 결과는 비워두고 작성 안내를 표시한다. 설명용 예시는 명시적으로 구분한다. |
| 필수 정보 부족 | 해당 항목 아래에 오류를 표시하고 입력을 보존한다. |
| 생성 중 | 버튼 중복 실행을 막고 진행 상태를 표시한다. |
| 생성 완료 | 초안 3개를 보여주고 제목·본문·마지막 안내·해시태그를 수정할 수 있게 한다. |
| 상품 정보 변경 | 기존 초안이 이전 입력으로 만들어졌음을 표시한다. 편집 중인 내용은 보존한다. |
| 재생성 | 새 요청 결과가 성공한 뒤 결과 목록을 교체한다. 실패하면 기존 편집 내용을 유지한다. |
| 연결·시간·형식 오류 | 입력을 유지하고 실패 이유와 다시 시도 버튼을 제공한다. 부분 응답을 완료된 광고로 표시하지 않는다. |
| 저장 | 사용자가 선택하고 수정한 결과만 복사·TXT·PNG에 반영한다. 모델 원문을 대신 저장하지 않는다. |

PNG는 선택한 실제 상품 사진 또는 ‘참고 코디’ 표시가 있는 3D 이미지와 편집한 문구를 조합한다. 모델이 이미지를 새로 생성하는 기능은 이 단계에 포함하지 않는다.

## 6. 모델 연결 설계

- 사용자는 2026-09-16 대화에서 교육 과정 제공 OpenAI API 사용 가능을 확인했다.
- 시작 모델은 과제 가이드의 허용 목록에 있는 `gpt-5-mini`로 선정한다. 이는 교육 계정의 범위에 맞춘 선택이며, 2026-09-29에 활성 프로젝트의 키로 실제 호출이 가능함을 확인했다.
- 서버에서 Responses API를 호출하고, Structured Outputs로 초안 필드의 형식을 지정한다. 추론 강도는 `low`, 응답 대기 한도는 45초다. 공식 모델 문서는 해당 모델의 Responses·Structured Outputs 지원을 명시한다. [모델 문서](https://developers.openai.com/api/docs/models/gpt-5-mini)
- 모델에 전달할 출력 스키마는 루트를 객체로 두고, 객체의 모든 필드를 필수로 지정하며, 추가 필드를 허용하지 않는다. 문자 수·초안 관점의 중복 등은 응답을 받은 뒤 애플리케이션에서도 검사한다. [Structured Outputs 공식 문서](https://developers.openai.com/api/docs/guides/structured-outputs#supported-schemas)
- 입력에 포함된 지시문을 상품 데이터로 취급하고 시스템 지시로 실행하지 않는다. 생성 실패 시 고정 문구를 실제 AI 결과처럼 대체하지 않는다.
- API 키는 서버 환경변수(`OPENAI_API_KEY`)로만 관리하고 코드·Git·문서에 넣지 않는다. 서버 경로는 키가 없으면 예시 문구를 대신 보여주지 않고 "연결 설정 필요"를 돌려준다.
- 상품 텍스트와 광고 조건만 생성 요청에 포함한다. 체형 수치, 체형 사진, 원본 상품 사진은 포함하지 않는다.
- 운영 로그에는 처리 시간, 결과 상태, 모델·프롬프트 버전, 사용량을 남기는 방향으로 설계한다. 원본 사진과 키를 기록하지 않는다.

## 7. 개발용 규격과 검증

- [contracts.mjs](ads/contracts.mjs): 기존 프로젝트의 Zod로 작성한 입력·결과 검사 설계안.
- [model-response.schema.json](ads/model-response.schema.json): 향후 모델 요청에 사용할 출력 JSON Schema.
- [evaluation-cases.json](ads/evaluation-cases.json): 정상 4개·오류 4개의 고정 평가 입력.
- [check-contract.mjs](ads/check-contract.mjs): 예시와 입력·결과 오류 처리를 검증하는 로컬 실행 파일.

```sh
node docs/ads/check-contract.mjs
```

이 파일들은 초기 설계용 실행 예시다. 실제 사이트의 요청·응답 검사는 `lib/ads/contracts.ts`와 `app/api/ads/generate/route.ts`로 옮겼다. 규격 검사가 API 연결 성공·생성 품질·광고 사실 검증을 증명하지는 않으므로 고정 평가 입력으로 별도 측정한다(2026-09-29 1차 결과는 [평가 요약](evaluations/runs/2026-09-29T00-23-32-748Z.md), 9/30 재평가의 버전별 비교는 [평가 안내](evaluations/README.md)).

## 8. 구현 상태와 다음 순서

1. 완료: 판매자 입력 화면과 기본값·필수 항목 검사.
2. 완료: 서버의 API 경로와 출력 형식 검사, 실패·재시도 처리.
3. 완료: 초안 선택·편집과 복사·TXT·PNG 저장.
4. 완료: 정상 입력 4개를 실제 생성해 형식·속도를 측정했고(평균 19.1초), 사실 보존·말투·활용 가능성은 Codex 보조 검토로 1차 기록했다. 이후 9/30에 프롬프트를 다섯 번 고쳐 다시 생성했고(평균 약 7초, 추론 강도 `low`) 사람의 최종 점수 확인은 남아 있다.
5. 완료: 등록 상품 선택기. 판매자가 등록한 상품의 사실 정보(상점명·상품명·종류·색상·특징·소재·가격)만 불러오고 할인율은 직접 입력한다. 사진을 고르기 전에는 종류별 "참고 이미지"를 표시하고 PNG 카드에도 그렇게 적는다.
6. 다음: 배포 환경에 서버 비밀값 연결 후 실제 사이트에서 생성 확인. 같은 입력 3회 반복은 9/30 재평가에서 프롬프트 2026-09-30.2판부터 했다.
